# OneLibrary round trips, DDJ-GRV6 controls and quality STEMS

This study uses the recordbox 0.9.0 candidate `91c8e97`. The three tests answer different questions a DJ can encounter when preparing a USB drive, connecting a controller or seeking to a hot cue. [Fork candidate](https://github.com/fantuz/recordbox/pull/28) · [Upstream revision reviewed](https://github.com/adamsardo/recordbox/tree/4b71b0158d89ab35dafa7d54636c684ba0053318)

## OneLibrary on a USB drive

**A classic rating edit left the OneLibrary catalog byte-for-byte intact.** We copied a published mixed Rekordbox 7 export, changed classic track 1 from zero to one star in recordbox, then reopened both catalogs. The two classic PDB files changed. The other 12 files had identical SHA-256 hashes, including the 118,784-byte `PIONEER/rekordbox/exportLibrary.db`, six analysis files and four player settings files. We replayed the existing mixed-device regression twice using a cached Linux test build from 26 November. Its test source matches the candidate. [Fixture](https://github.com/dylanljones/rbox/tree/9677e21448fe3a8462111b7df099b5608efcba90/.testdata/RBv7/demo/export) · [Regression test](https://github.com/fantuz/recordbox/blob/91c8e9789937151119ea60118263902bc38428d1/app/src/export/public_device_tests.rs)

| Observation | What was verified |
| --- | --- |
| Classic catalog | An independent Crate Digger schema reader saw the one-star change on track 1. The playlist still contained track 1 followed by track 2. The recordbox test checked six cues in classic ANLZ files. |
| OneLibrary catalog | An independent read-only SQLCipher inspection found the same schema and all 110 rows across 22 application tables before and after. `property.dbVersion` was 1000, both track ratings stayed at zero, and the playlist still contained track 1 followed by track 2. `quick_check` passed and `foreign_key_check` returned zero rows. |
| Fixture coverage | The OneLibrary cue, hot-cue bank and history tables were empty. The export contains no playable audio. Verification of populated relationships and playback needs a different fixture. |

**A playlist reorder also survived a real OneLibrary write and reopen.** On a fresh disposable copy of the same export, the published `rbox` 0.3.1 library moved content 2 to position 1 of playlist 1 using its documented `move_playlist_content(1, 2, 1)` API. After the writer exited, a separate read-only SQLCipher process saw the order change from `[1, 2]` to `[2, 1]`. Only the two `playlist_content.sequenceNo` values changed. A second writer moved the track back with `move_playlist_content(1, 2, 2)`. Reopening restored the original logical contents of every table. The encrypted file had a different hash, while all 13 sibling files retained theirs. The classic playlist therefore kept its original order throughout. This check exercised the external writer on `dbVersion` 1000. Native Rekordbox and standalone-player acceptance are still open. [Published Python package](https://pypi.org/project/rbox/0.3.1/) · [One-based playlist operation](https://github.com/dylanljones/rbox/blob/9677e21448fe3a8462111b7df099b5608efcba90/crates/rbox-onelib/src/database.rs#L1043-L1060)

The read-only order check after each reopen was `SELECT playlist_id, sequenceNo, content_id FROM playlist_content ORDER BY playlist_id, sequenceNo`. We also compared the complete application tables, checked schema objects and referential integrity, and only inspected closed databases with no pending WAL frames. A future recordbox implementation can use this sequence as a reference test without adding the external writer as a product dependency.

**What to reuse from Library Workbench.** Its bounded file inspection can inventory the classic catalog, companion ANLZ and player settings on an export or in a backup ZIP. On both snapshots it recognized two DeviceSQL headers, six analysis files and four settings files. For OneLibrary it recognized the filename and reported the contents as unsupported. Crate Digger already helps validate classic DeviceSQL. Its archive tool copies the OneLibrary file. Deep Symmetry's separate Beat Link project actually reads OneLibrary, including looking up an analysis path by track ID. The public `rbox-onelib` schema is another concrete reference for the observed database version. These sources have distinct roles and licenses. [Workbench inspector](https://github.com/fantuz/rekordbox-migration-helper/blob/f026dbff07107d39536dad846ceb1d28095e9185/asset_formats.py#L78-L94) · [Crate Digger archive](https://github.com/Deep-Symmetry/crate-digger/blob/7c9d5358d8a3ce663f566380f2dc79ab1393201e/src/main/java/org/deepsymmetry/cratedigger/Archivist.java#L177-L180) · [Beat Link lookup](https://github.com/Deep-Symmetry/beat-link/blob/1483c006162237bd2681aab95288c345241bcd2d/src/main/java/org/deepsymmetry/beatlink/data/CrateDigger.java#L509) · [rbox schema and device tests](https://github.com/dylanljones/rbox/tree/9677e21448fe3a8462111b7df099b5608efcba90/crates/rbox-onelib)

### The first native round trip to qualify

1. In AlphaTheta Rekordbox, export two short self-created tracks to a spare drive. Put both tracks in one playlist, give them distinct cues, and record the export application version and catalog type. Eject cleanly and take a complete baseline copy. Where a player creates history, capture one populated history as well.
2. On a disposable copy, use official Rekordbox to reverse just the two playlist entries. Eject and capture again. Compare content IDs, playlist ID and member order, cue and history relationships, analysis paths and the hashes of audio and other files. Record any additional changes the official software makes. For an edited encrypted database, compare logical contents across reopen as well as file hashes. Skip **Convert from Device Library** for this test because it can overwrite device-only playlists and histories. [AlphaTheta conversion FAQ](https://rekordbox.com/en/support/faq/onelibrary-7/) · [Official USB export guide](https://cdn.rekordbox.com/files/20251021171528/USB_export_guide_en_251007.pdf)
3. A candidate OneLibrary writer would have to reproduce that observed edit on a fresh copy of the baseline, preserve the other data, and decline unknown schema versions. Reopen with official Rekordbox, browse the reordered playlist and load both tracks on the intended standalone player. Record model and firmware. Then reopen the player's ejected drive to check any new history against the track actually played. The DDJ-GRV6 uses a host computer for playback. This player check needs separate hardware. [AlphaTheta equipment list](https://rekordbox.com/en/support/usb-export/)

To repeat the existing **classic-edit preservation test**, set `RECORDBOX_TEST_RBOX` to the pinned rbox checkout above and run this in the recordbox source tree.

```sh
cargo test --manifest-path app/Cargo.toml --locked -- --ignored --exact export::public_device_tests::mixed_export_keeps_onelibrary_and_shared_anlz_intact
```

## Physical MIDI on the AlphaTheta DDJ-GRV6

The follow-up MIDI study compares the same two-deck messages on the fork and upstream, then measures the cost of updating controller feedback. [MIDI replay results and reproduction](midi-replay/README.md)

The candidate passed a native Intel macOS **virtual** CoreMIDI exchange for transport, hot cues, mixer, jogs, feedback and disconnect. We also replayed the actual GRV6 bytes below against the candidate's mapping code, using a small independently written two-deck mapping. With no factory or user mapping, the software ignored PLAY. With the test map, it decoded input for each deck and encoded the expected LED bytes. A Linux integration test also imported the CSV through the candidate’s normal mapping path. PLAY toggled only the addressed deck. Rim and platter packets bent that deck in both directions and its engine returned to neutral at the idle deadline. Physical response, audio latency, decks 3/4 and Groove Circuit remain unverified. The candidate's MIDI action registry has no dedicated Drum Swap or Drum Capture action. [Native CI run](https://github.com/fantuz/recordbox/actions/runs/46036491081/job/140633314533#step:13:1) · [MIDI registry](https://github.com/fantuz/recordbox/blob/91c8e9789937151119ea60118263902bc38428d1/app/src/midi.rs#L357-L592) · [AlphaTheta message list, pages 1–3](https://downloads.support.alphatheta.com/software_info/dj-controllers/DDJ-GRV6/DDJ-GRV6_MIDI_Message_List_E1.pdf)

| Control, Shift released | Deck 1 | Deck 2 | Expected result |
| --- | --- | --- | --- |
| PLAY and CUE | `90 0B` and `90 0C` | `91 0B` and `91 0C` | Last byte `7F` on press, `00` on release. PLAY and CUE LEDs use the corresponding notes. |
| Jog rim / platter top with vinyl off | `B0 21` / `B0 23` | `B1 21` / `B1 23` | Last byte `41` gives +1 and `3F` gives −1. The rim and top send different controller numbers. |
| Channel fader | `B0 13`, `B0 33` | `B1 13`, `B1 33` | Paired high and low bytes decoded to 0, 8192 and 16383 at the test positions. |
| Hot Cue pad 1 | `97 00` | `99 00` | With Hot Cue mode selected, `7F` and `00` give press and release. The same note addresses the pad LED. |

**First physical check.** Connect the GRV6 by its USB-C **device connection** port and close other DJ apps using the controller. On Linux, `aseqdump -l` lists the inputs. `aseqdump -p CLIENT:PORT` listens to the selected input. Press PLAY and CUE on each deck and turn the unshifted rim both ways. Stop the monitor before opening recordbox. On any supported desktop, open PERFORMANCE, load a short local track at low output volume and verify that a physical PLAY press toggles its deck exactly once. Then toggle PLAY **with the mouse** and watch the controller's LED. That distinguishes feedback from a light that follows a physical press locally. Turn the rim during playback, let go and verify that the tempo returns to normal. Disconnect and reconnect with both decks paused and repeat one PLAY press. [GRV6 ports](https://downloads.support.alphatheta.com/manuals/dj-controllers/DDJ-GRV6/DDJ-GRV6_DRI1927A_manual.pdf#page=51) · [Third-party MIDI operation](https://downloads.support.alphatheta.com/manuals/dj-controllers/DDJ-GRV6/DDJ-GRV6_DRI1927A_manual.pdf#page=170) · [ALSA monitor](https://manpages.debian.org/trixie/alsa-utils/aseqdump.1.en.html)

Use the installed GRV6 mapping if available. For an isolated check without it, start the candidate with `PREPDECK_DATA` pointing at a new empty folder, open the MIDI window, select the GRV6 and import the study CSV. Import writes a local mapping for the selected device. This sample covers only the controls in the table. MIDI Learn can assign basic transport. The jog actions require a mapping. Record the firmware, OS, input and output port names, mapping used, on-screen response and observed LED. A latency measurement also needs the actual audio output on the same timing reference as the press. [Download the two-deck study CSV](DDJ-GRV6-two-deck-check.csv?raw=1) · [Mapping selection](https://github.com/fantuz/recordbox/blob/91c8e9789937151119ea60118263902bc38428d1/app/src/midi.rs#L1045-L1075)

To start with a fresh test profile on Linux, run `PREPDECK_DATA="$(mktemp -d)" ./recordbox`. On Windows, open a new PowerShell in the folder containing the candidate and run the following. Closing that shell ends the environment override.

```powershell
$env:PREPDECK_DATA = Join-Path ([IO.Path]::GetTempPath()) ("recordbox-grv6-" + [guid]::NewGuid())
.\recordbox.exe
```

Upstream also added a read-only survey that compares installed mapping rows with implemented input actions and LED sources. This is worth using to inventory the rest of the GRV6 controls when its factory profile is available. Check that the profile was included in the file set. The survey returns successfully when it finds zero files, and its totals span all scanned devices. ## Fast access to quality STEMS

Quality runs four specialist HTDemucs networks. The fork runs each specialist across the entire track in turn and starts publishing playable audio during the fourth pass on eligible hardware. Upstream runs all four specialists on one window before moving on. Its quality mode still processes windows in track order. The two later upstream commits through `4b71b01` leave these STEMS scheduling functions intact. [Fork specialist loop](https://github.com/fantuz/recordbox/blob/91c8e9789937151119ea60118263902bc38428d1/app/src/stems/mod.rs#L464-L497) · [Upstream scheduler](https://github.com/adamsardo/recordbox/blob/4b71b0158d89ab35dafa7d54636c684ba0053318/app/src/stems/mod.rs#L597-L649)

| Playback position on a four-minute track | Fork quality | Upstream quality | Proposed quality with playhead priority |
| --- | ---: | ---: | ---: |
| Start | 127 | 4 | 4 |
| 2 min 56 s, inside an overlap | 157 | 124 | 8 |
| 3 min, inside one window | 157 | 124 | 4 |
| Whole track | 168 | 168 | 168 |

These are **network-window evaluations**, a count of work needed before the requested samples are final. The comparison used the production window planner and upstream selector, one stationary playhead present at job start, no competing requests, 44.1 kHz and a 512-frame margin on either side. A 343,980-frame window with 25% overlap advances by 257,985 frames. Four minutes gives 42 windows. The fork reaches the start after `3 × 42 + 1` evaluations. A cue in an overlap needs contributions from both windows across all four specialists. Counts account for the respective 8,192- and 4,096-frame publication blocks. The fork's 512 MiB cap covers a prefix of about 6 min 20 s. A cue beyond it waits for the finished result. [Window planner](https://github.com/fantuz/recordbox/blob/91c8e9789937151119ea60118263902bc38428d1/app/src/stems/htdemucs.rs#L712-L720) · [Fork preview budget](https://github.com/fantuz/recordbox/blob/91c8e9789937151119ea60118263902bc38428d1/app/src/stems/live.rs#L10-L74) · [Upstream overlap finalization](https://github.com/adamsardo/recordbox/blob/4b71b0158d89ab35dafa7d54636c684ba0053318/app/src/stems/htdemucs.rs#L711-L743)

**Measured CPU cost.** On a four-core-quota Intel Xeon Platinum 8573C, the first window took **22.48 s** with the speed checkpoint and **79.66 s combined** across the four quality checkpoints. This was one optimized CPU run using real weights and a generated 12-second stereo signal at 44.1 kHz (220 Hz left, 329.63 Hz right, amplitude 0.2). We timed `separate` through its first completed window on each checkpoint, loading one graph at a time. Individual loads took 0.40–1.03 s and were timed separately. These are inference timings for one window. Audible latency on a GPU, output correctness after reordering and whole-track elapsed time still need measurement. [Model catalog](https://github.com/fantuz/recordbox/blob/91c8e9789937151119ea60118263902bc38428d1/app/src/stems/mod.rs#L270-L303) · [Separation callback](https://github.com/fantuz/recordbox/blob/91c8e9789937151119ea60118263902bc38428d1/app/src/stems/htdemucs.rs#L782-L815)

**First implementation to test.** Play the original immediately, use a matching finished quality cache first, and prioritize all four specialists for the playback region on a GPU with measured headroom. Publish a region only after every contributing overlap is final. A sparse set of immutable preview blocks could serve a late cue within the same memory cap. Start opt-in on one modern Metal or CUDA machine. Keep the existing lower-memory completed-job path for CPU, Vega and the P2000. On the same track and model, measure time to the first *audible* four stems, time after a late seek, whole-track time, peak memory and audio underruns. Compare boundary samples and the completed output against the existing pipeline. Unload, cancellation, two decks and cache reload are separate acceptance cases.
